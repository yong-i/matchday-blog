## 1. 발표 피드백을 받고 바꾼 방향

1편에서는 사용자가 방문할 장소와 이동 시간을 입력하면 경기장 도착 시각을 계산하는 서비스를 기획했다. 가고 싶은 장소들을 들렀다가 경기장에 여유 있게 도착할 수 있는지 확인하는 것이 출발점이었다. [블로그 1편]({{ '/project-proposal/' | relative_url }})

11월 3일 발표에서 교수님은 지도 API로 이동 시간을 가져오는 방식을 제안하셨다. 경기장과 경기 시작 시각을 입력하면 AI가 그 전에 할 일을 추천하는 방식도 이야기해 주셨다. 이를 반영해 사용자가 코스를 직접 작성하는 기능에 더해, AI가 방문할 장소와 순서, 체류 시간을 제안하는 방향으로 구체화했다.

이번 데이터 설계는 야구장 한 곳을 첫 대상으로 잡았다. 경기장, 경기 시작 시각, 출발 장소와 시각을 입력하고 식비 예산과 입장 여유 시간을 정하면, 미리 등록한 식당·카페 중에서 코스를 제안받는 상황이다. 최종 코스의 이동·체류 시간을 합산해 경기장 도착 예정 시각을 확인하고, 사용자가 확정한 계획을 저장할 예정이다.

이 글에서는 그 기능을 만들기 위해 어떤 데이터를 나누어 저장할지, 테이블을 어떻게 연결할지, AI와 설계를 검토하면서 어떤 점을 바꿨는지 정리한다.

## 2. 사용자 행동에서 필요한 데이터 찾기

먼저 화면에서 사용자가 하는 행동을 기준으로 저장할 내용을 정리했다.

| 사용자 행동 | 필요한 데이터 |
| --- | --- |
| 관람할 경기장 선택 | 경기장 이름, 위치 좌표 |
| 하루 계획 입력 | 출발 장소와 시각, 경기 시작 시각, 입장 여유 시간, 식비 예산 |
| 코스 추천 요청 | 등록한 장소 후보, 위 조건을 담은 추천 요청 |
| 식당·카페 방문 계획 수정 | 방문 장소, 순서, 이동·체류 시간, 예상 식비 |
| 경기장 도착 시각 확인 | 방문 항목의 이동·체류 시간, 마지막 경기장 이동 시간 |
| 확정한 코스 저장·조회 | 관람 계획과 그 계획에 속한 방문 항목 |

여기서 장소의 정보와 방문의 정보가 다르다는 점을 구분했다. 카페의 이름과 위치는 여러 계획에서 공유할 수 있다. 반면 카페에 몇 번째로 가는지, 얼마나 머무는지, 얼마를 쓸지는 계획마다 달라질 수 있다. 이 차이를 데이터 구조에 반영하려고 했다.

## 3. ERD 초안과 테이블 관계

![직관 가는 날 ERD 초안. 경기장과 계획, 계획과 일정 항목, 장소와 일정 항목이 연결된다.]({{ '/assets/images/matchtrip-erd.svg' | relative_url }})

데이터는 네 테이블로 나누었다. `PK`는 각 행을 구분하는 기본키이고, `FK`는 다른 테이블의 행을 가리키는 외래키다.

| 테이블 | 저장하는 정보 | 다른 테이블과 연결 |
| --- | --- | --- |
| `stadiums` | 경기장 이름과 위도·경도 | 여러 관람 계획이 같은 경기장을 선택 |
| `plans` | 관람 계획 전체의 시간·예산 조건 | 경기장 하나를 선택하고 여러 일정 항목을 포함 |
| `places` | 식당·카페의 이름, 분류, 좌표, 예상 식비 기본값 | 여러 일정 항목에서 같은 장소를 사용 |
| `plan_items` | 특정 계획에서의 방문 순서와 이동·체류 시간, 적용 식비 | 관람 계획 하나와 장소 하나를 연결 |

경기장 하나를 여러 계획에서 선택할 수 있으므로 `stadiums`와 `plans`는 1 대 다 관계다. 계획 하나에는 여러 방문 항목이 들어가므로 `plans`와 `plan_items`도 1 대 다 관계다. 같은 카페를 서로 다른 계획에서 방문할 수 있어 `places`와 `plan_items` 역시 1 대 다 관계로 연결한다.

예를 들어 계획 A에서 카페 B를 25분 방문하고, 계획 C에서 같은 카페 B를 45분 방문할 수 있다. 카페 B의 이름과 좌표는 `places`에 한 번 저장하고, 두 번의 방문은 각각 다른 `plan_items` 행으로 저장하는 방식이다.

## 4. 각 테이블에 넣을 필드

아래는 구현을 위한 필드 초안이다. 시간과 비용의 단위를 이름에 표시해 계산할 때 혼동을 줄이려고 했다. `_min`은 분, `_won`은 원 단위다.

### 경기장 · stadiums

| 필드 | 의미 |
| --- | --- |
| `id` | 경기장 기본키 |
| `name` | 경기장 이름 |
| `latitude` | 경기장 위도 |
| `longitude` | 경기장 경도 |

경기장 이름과 좌표를 모든 계획에 반복해서 적는 대신 경기장 테이블로 묶었다. 관람 계획은 `stadium_id`로 경기장을 가리킨다. 마지막 방문지에서 경기장까지 이동 시간을 조회할 때 목적지 좌표를 여기서 가져올 계획이다.

첫 버전에서는 선택 가능한 경기장이 한 곳이어도 이 구조를 유지한다. 나중에 대상을 늘리면 경기장 정보를 추가하고, 각 경기장 주변의 장소 후보를 구성하는 방법도 함께 검토할 예정이다.

### 관람 계획 · plans

| 필드 | 의미 |
| --- | --- |
| `id` | 관람 계획 기본키 |
| `stadium_id` | 방문할 경기장의 외래키 |
| `start_label` | 일정의 출발 장소 이름 |
| `start_at` | 출발 날짜와 시각 |
| `game_at` | 경기 시작 날짜와 시각 |
| `entry_buffer_min` | 경기 시작 전에 확보하려는 입장 여유 시간 |
| `food_budget_won` | 사용자가 정한 식비 예산. 선택하지 않으면 비워 둠 |
| `manual_last_leg_min` | 사용자가 직접 입력한 마지막 경기장 이동 시간. 입력하지 않으면 비워 둠 |

출발과 경기 시각은 날짜를 함께 다루고, 첫 범위는 한국 시간 기준 같은 날짜의 경기 전 일정으로 정했다. 목표 도착 시각은 경기 시작 시각에서 입장 여유 시간을 빼서 계산한다. 예를 들어 18시 경기에서 30분의 여유를 원하면 목표는 17시 30분이다.

식비 예산이 비어 있으면 예산 초과 비교를 생략하고, 0원을 입력했다면 0원을 기준으로 비교할 계획이다. 마지막 이동 시간도 비어 있는 상태와 0분을 입력한 상태를 구분하려고 한다.

### 방문 장소 · places

| 필드 | 의미 |
| --- | --- |
| `id` | 장소 기본키 |
| `name` | 식당·카페 이름 |
| `category` | 식당 또는 카페 분류 |
| `latitude` | 장소 위도 |
| `longitude` | 장소 경도 |
| `default_food_cost_won` | 코스에 추가할 때 참고할 1인 예상 식비 기본값 |

AI가 추천할 장소 후보도 이 테이블에서 가져올 계획이다. 첫 버전은 해당 경기장 주변에서 직접 정리한 후보 목록으로 시작한다. AI에게는 후보의 ID와 분류, 예상 식비 등을 전달하고, 결과로 받은 ID가 실제 등록된 장소인지 확인한다.

예상 식비의 기본값은 코스를 구성할 때 참고할 값이다. 사용자가 이번 방문 비용을 바꾸면 그 값은 해당 일정 항목에 적용한다. 이렇게 하면 장소의 기본값을 바꿔도 이미 저장한 계획의 적용 식비가 함께 바뀌는 문제를 줄일 수 있다.

### 일정 항목 · plan_items

| 필드 | 의미 |
| --- | --- |
| `id` | 일정 항목 기본키 |
| `plan_id` | 이 항목이 속한 관람 계획의 외래키 |
| `place_id` | 방문할 장소의 외래키 |
| `position` | 해당 계획 안에서의 방문 순서 |
| `travel_min` | 직전 지점에서 이 장소까지의 예상 이동 시간 |
| `stay_min` | 이 장소에서 머무는 시간 |
| `food_cost_won` | 이번 방문에 적용할 1인 예상 식비 |

첫 항목의 `travel_min`은 출발 장소에서 첫 방문지까지의 이동 시간이다. 두 번째 항목부터는 앞 방문지에서 현재 방문지까지의 이동 시간이다. 방문지를 바꾸거나 순서를 바꾸면 이 이동 시간도 다시 확인하도록 할 예정이다.

순서는 같은 계획 안에서만 중복을 막는다. 다른 계획에서 각각 1번 순서를 쓰는 것은 가능하지만, 한 계획에 1번 항목 두 개를 넣으면 방문 순서를 해석하기 어렵다. 구현할 때는 `plan_id`와 `position` 조합에 중복 방지 조건을 적용할 계획이다.

## 5. 코스를 추천하고 저장하는 흐름

사용자가 관람 조건을 입력하면 백엔드가 장소 후보와 조건을 AI에 전달한다. AI는 방문할 장소 ID, 방문 순서, 체류 시간을 제안한다. 반환된 장소 ID가 후보에 있는지, 순서와 체류 시간이 유효한지 앱에서 확인한다.

첫 연동 범위에서는 출발지부터 방문지까지의 이동 시간을 사용자가 입력한다. 마지막 방문지에서 경기장까지의 도보 시간은 두 지점의 좌표로 조회하는 방식을 검토하고 있다. 현재 후보는 TMAP의 보행자 경로 API다. [TMAP 공식 가이드](https://tmapapi.tmapmobility.com/main.html)

모든 구간의 이동 시간과 각 장소의 체류 시간이 정해지면 예상 도착 시각과 식비 합계를 계산한다. 목표 시각이나 예산을 넘기면 어느 조건을 초과했는지 표시하고, 사용자가 체류 시간이나 코스를 조정할 수 있게 할 예정이다.

사용자가 코스를 확정하면 `plans`와 그에 속한 `plan_items`를 한 트랜잭션으로 저장할 계획이다. 예를 들어 계획만 저장되고 카페 항목 저장은 실패하면, 다시 열었을 때 원래 코스와 다른 내용이 된다. 저장 도중 실패하면 전체 저장을 취소하도록 해 이런 상태를 막으려고 한다.

계획을 다시 열 때는 계획 조건과 일정 항목을 불러오고, 항목을 `position` 순으로 정렬한다. 지도 API의 응답과 계산한 도착 시각은 별도 필드에 저장하지 않고 다시 조회·계산하는 방향이다. API 호출이 실패하면 마지막 구간의 예상 시간을 사용자가 입력할 수 있게 한다. 직접 입력한 값은 `manual_last_leg_min`에 저장하고 화면에 입력값임을 표시한다. 이후 다시 자동 조회를 사용할 때는 직접 입력한 대체값을 해제하도록 할 계획이다.

## 6. 가상 데이터로 확인한 시간 계산

다음은 설계를 확인하기 위한 가상의 코스다. 특정 업체의 가격이나 실제 API에서 받은 이동 시간은 아니다.

출발은 15시 30분, 경기는 18시이고 30분 전에 도착하려고 한다. 목표 도착 시각은 17시 30분, 식비 예산은 30,000원이다.

| 순서 | 직전 지점에서 이동 | 체류 | 방문 시간 | 예상 식비 |
| --- | --- | --- | --- | --- |
| 식당 | 10분 | 45분 | 15:40~16:25 | 12,000원 |
| 카페 | 10분 | 25분 | 16:35~17:00 | 6,000원 |
| 경기장 도착 | 도보 20분으로 가정 | — | 17:20 | — |

이 계획에서는 이동과 체류에 총 110분이 걸려 17시 20분에 도착한다. 목표보다 10분 여유가 있고 예상 식비는 18,000원이다.

Codex를 통해 임시 SQLite에 가상 데이터를 넣고, 다음 결과가 계산되는지 확인했다.

| 바꾼 조건 | 예상 도착 | 목표 17:30과 비교 |
| --- | --- | --- |
| 카페 체류 25분 | 17:20 | 10분 여유 |
| 카페 체류를 20분 늘려 45분 | 17:40 | 10분 초과 |
| 그 상태에서 10분 줄여 35분 | 17:30 | 목표 시각과 같음 |

입장 여유 시간까지 반영하려면 경기 시작 시각과 목표 도착 시각을 구분해 계산해야 한다. 17시 40분 도착은 18시 경기 시작 전이지만, 사용자가 원한 30분의 여유에는 10분이 부족하다. 이 경우에는 입장 목표를 넘겼다고 표시하려고 한다.

## 7. 잘못된 데이터를 막기 위한 규칙

계산에 사용할 값의 범위를 정하는 것도 데이터 설계에 포함했다. 임시 DB에서는 같은 계획의 방문 순서 중복, 등록되지 않은 장소 참조, 음수 체류 시간 입력을 거부하는지 확인했다. 검증을 위해 의도적으로 잘못된 값을 넣은 테스트다.

| 입력 상황 | 적용할 처리 | 현재 확인 범위 |
| --- | --- | --- |
| 한 계획에 같은 방문 순서를 두 번 입력 | 중복 저장 거부 | 임시 SQLite에서 확인 |
| 존재하지 않는 장소 ID를 저장 | 외래키 조건으로 거부 | 임시 SQLite에서 확인 |
| 체류 시간에 음수 입력 | 저장 거부 | 임시 SQLite에서 확인 |
| 출발 시각이 입장 목표 시각보다 늦음 | 가능한 일정인지 안내하고 조건 수정 요청 | 서비스 구현 시 확인 예정 |
| 마지막 이동 시간을 조회하지 못함 | 직접 입력하도록 안내 | 지도 API 연동 후 확인 예정 |

실제 서비스 DB는 교수님이 제시한 구성에 맞춰 PostgreSQL을 사용할 계획이다. 지금의 검증은 테이블 연결과 계산 예시를 임시 DB에서 확인한 것이다. PostgreSQL에 연결할 때도 외래키와 순서 중복 방지 조건, 저장·조회의 동작을 다시 확인하겠다.

## 8. AI와 검토하면서 구체화한 부분

Codex에는 교수님 피드백과 응원팀 테마 아이디어를 반영해 11월 9일 제출분을 진행해 달라고 요청했다. 이어서 교수님이 보여주신 백엔드·프론트엔드·PostgreSQL·Docker 구성을 전달했다. 이 글의 초안 작성, ERD와 필드 정리, 임시 DB 검증은 Codex의 도움을 받았다. 내가 전달한 발표 피드백과 직접 제안한 테마 아이디어를 바탕으로, 각 값이 어느 테이블에 들어가는지와 기능별 데이터 흐름을 구체화했다.

| 처음 검토한 내용 | 이번 초안에서 구체화한 내용 | 이유 |
| --- | --- | --- |
| 관람 계획·장소·일정 항목의 세 테이블 | 경기장 테이블을 추가 | 이름과 목적지 좌표를 여러 계획에서 공유하기 위해 |
| 장소와 방문 정보를 구분해야 함 | 체류 시간과 적용 식비를 일정 항목에 저장 | 같은 장소라도 방문별 값이 달라지기 때문에 |
| 사용자가 이동 시간을 입력 | 마지막 경기장 구간부터 지도 API 적용 검토 | 기존 계산 흐름에 실제 조회값을 연결하기 위해 |
| 코스를 직접 작성 | 등록한 장소 후보에서 AI 추천 추가 | 추천한 장소를 확인하고 일정 조건을 계산하기 위해 |
| 임시 DB로 설계 확인 | 실제 서비스 DB는 PostgreSQL로 계획 | 교수님이 제시한 개발 구성에 맞추기 위해 |

이 초안을 검토하면서 내가 직접 설명할 수 있어야 할 부분은 장소 정보와 방문 정보의 차이라고 생각한다. 카페 이름과 위치를 바꾸는 일과, 이번 계획에서 카페 체류 시간을 바꾸는 일은 영향을 받는 데이터의 범위가 다르다. 이 구분을 이해하고 이후 구현에서도 유지하려고 한다.

## 9. 응원팀 테마는 경기장 선택과 별도로

개인적으로 화면 왼쪽 상단에서 응원하는 야구 구단을 선택하면 구단의 색상과 분위기에 맞춰 UI가 바뀌면 좋겠다고 생각했다. 원정 직관을 가는 날에도 내가 응원하는 팀의 테마를 유지할 수 있도록, 응원팀 선택과 방문 경기장 선택을 따로 두려고 한다.

테마를 바꾸는 것은 계획의 경기장이나 방문 코스를 바꾸는 동작과 구분한다. 추후 기능으로 두고, 처음에는 브라우저에 테마 선택을 기억시키는 방식을 고려한다. 따라서 이번 ERD에서는 화면 테마를 위한 사용자나 구단 테이블을 추가하지 않았다.

첫 커밋을 GitHub에도 올려 기획과 설계 자료를 확인할 수 있게 했다. [프로젝트 저장소](https://github.com/yong-i/matchtrip)

교수님이 보여주신 구성에 맞춰 프론트엔드는 계획 입력과 코스 결과를 표시하고, 백엔드는 PostgreSQL 저장·조회, 시간 계산, AI와 지도 API 호출을 담당하도록 만들 계획이다. 모바일 사용은 휴대폰 브라우저의 화면 크기에 맞춰 입력창과 결과가 배치되는 반응형 웹으로 구현하려고 한다. Docker로 실행 환경을 구성하고, DB 데이터는 별도 볼륨에 저장하며, API 키와 DB 비밀번호는 서버 환경변수로 관리할 예정이다.

현재까지 확인한 결과는 ERD 초안, 임시 DB에서의 가상 데이터 검증, 프로젝트 첫 커밋과 GitHub 업로드다. 다음에는 서비스 화면에서 코스를 입력하고 DB에 저장한 뒤 다시 조회하는 기능을 만들겠다. 이후 시간 계산과 초과 경고, 지도 API, AI 추천을 차례로 연결하면서 실제 실행 화면과 오류, 수정 과정을 기록할 예정이다. 11월 16일 첫 배포에서는 URL로 접속해 입력과 조회를 해볼 수 있는 버전을 목표로 한다.
