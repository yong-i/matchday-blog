## 1. URL로 열리는 첫 버전

**서비스 주소: <https://matchtrip-yong-i.onrender.com/>**

11월 9일에 처음 배포했고, 그 뒤 기능과 화면을 고쳐 11월 14일에 다시 배포했다. 무료 서버라 한동안 아무도 접속하지 않으면 잠들어서, 처음 열 때 1분 정도 걸릴 수 있다.

![직관 가는 날 첫 화면. 히어로 섹션에 "경기 전 코스, 제때 입장할 수 있을까?" 제목과 계산하러 가기 버튼, 오른쪽에 오늘의 경기 카드가 있다.]({{ '/assets/images/matchtrip-deploy-home.jpg' | relative_url }})

지금 할 수 있는 일은 다음과 같다.

- KBO 경기장 9곳 중 하나와 경기 시각, 출발지를 고른다. 출발지는 역 이름으로 검색해서 고르면 위치가 정해진다.
- 식사·카페·산책 중 하고 싶은 활동을 고르면, 경기장 근처의 실제 장소로 AI가 코스를 짜 준다.
- 출발지 → 방문지 → 경기장의 구간마다 도보 시간을 더해서, 입장 목표 시각에 맞게 도착하는지 계산한다.
- 계획을 저장하고 '내 계획'에서 다시 열어 고칠 수 있다. 경기마다 앉을 좌석을 '좌석 메모'에 적어 둘 수 있다.

## 2. 배포 구성

| 구분 | 사용한 것 | 고른 이유 |
| --- | --- | --- |
| 서버 | Render 웹 서비스(Docker, 무료) | 화면과 서버를 Docker 이미지 하나로 묶어 그대로 올릴 수 있어서 |
| 데이터베이스 | Neon PostgreSQL(무료) | Render 무료 DB는 30일 뒤 만료되어 DB를 따로 분리 |
| 장소·도보 경로 | TMAP API | 장소 검색, 주소 변환, 보행자 경로를 한 곳에서 제공 |
| 코스 추천 | Gemini API | 실제 검색된 후보 중에서만 코스를 고르게 하고 서버에서 다시 검증 |

API 키와 DB 접속 주소는 서버 환경변수에만 두고 GitHub에는 올리지 않았다. 배포는 자동이 아니라, 로컬에서 테스트를 통과한 뒤 직접 배포 버튼을 누르는 방식으로 했다. 서버가 시작될 때 DB 구조 변경(마이그레이션)이 적용되도록 했고, 이번 배포 뒤 공개 주소에서 경기장 9곳이 모두 나오는 것을 확인했다.

## 3. 2편 설계에서 달라진 것

2편에서는 사직야구장 한 곳, 미리 정리한 식당·카페 후보, 마지막 구간만 지도 API로 조회하는 구조를 계획했다. 실제로 만들면서 바뀐 점은 다음과 같다.

| 2편 계획 | 지금 | 바꾼 이유 |
| --- | --- | --- |
| 사직야구장 1곳 | KBO 주 경기장 9곳 | 원정 직관이 목적이라 모든 구장이 필요했다. 구장마다 가까운 역을 출발지 기본값으로 넣었다 |
| 마지막 구간만 도보 조회 | 모든 구간 도보 조회 | 방문지 사이 시간을 직접 넣으면 계산이 부정확했다 |
| 미리 정리한 장소 후보 | TMAP으로 실제 장소 검색 | 직접 정리한 목록은 금방 낡는다 |
| 장소마다 예상 식비 기본값 | 사용자가 식비를 입력 | 가격을 모르는데 가정값을 보여주면 오해할 수 있다. 지도에서 가격을 확인하고 입력하면 합계와 예산 초과만 계산한다 |
| 별점·리뷰 수 표시 | 표시하지 않음 | 제공되지 않는 경우가 많았다. 지도 링크로 직접 확인하게 했다 |

## 4. 막혔던 것과 푼 방법

**AI 응답이 안 올 때가 있었다.** 로컬에서 추천을 눌렀는데 Gemini가 "사용량이 많다"는 503 오류를 돌려줬고, 공개 서버에서는 AI 대신 조건 추천으로 바뀌어 있었다. 그래서 일시적인 오류일 때는 무료 등급의 다른 모델로 최대 3번까지 다시 시도하게 했다. 그래도 실패하면 시간·예산 조건으로 코스를 고르고, 화면에 어느 방식으로 추천했는지 표시한다.

**검색 반경을 넓혔더니 장소 검색이 실패했다.** 고정 2km 대신 남은 시간으로 걸어갈 수 있는 범위를 계산해서 TMAP에 반경을 3.5km처럼 소수로 보냈더니, "데이터 형식이 틀립니다"라는 400 오류가 났다. 가짜 응답으로 돌리는 자동 테스트에서는 드러나지 않았고, 실제 호출에서야 알았다. TMAP은 반경을 정수 km로만 받아서, 올림해서 보내고 정확한 범위는 받은 뒤에 거리로 걸러내게 고쳤다.

**부산역에서 출발하면 추천이 0곳이었다.** "출발지 → 장소"가 걸어서 3km 안이어야 한다는 조건 때문에, 멀리서 오는 사람은 후보가 하나도 없었다. 다른 지역에서 오는 사람이 원래 이 서비스가 생각한 사용자라서 꼭 고쳐야 했다. 지금은 먼 출발지면 경기장 근처에서 찾고, 첫 구간은 카카오맵 대중교통 길찾기 링크를 띄워 사용자가 시간을 입력하게 했다.

**대중교통 시간과 경기 일정은 자동으로 가져오지 못했다.** TMAP 대중교통 API의 무료 사용량은 하루 10건이라 시연에도 부족했다. 경기 일정을 모아 보여주는 기능도 만들려 했지만, KBO 홈페이지가 사전 승인 없이 데이터를 자동으로 수집하는 것을 금지하고 있어서 기능에서 뺐다.

## 5. 화면을 고칠 때 이름으로 요청하기

8강 '컴포넌트 이름편'을 듣고, 화면을 고쳐 달라고 할 때 일상어 대신 UI 이름과 동작, 조건을 함께 말하려고 했다.

| 처음 요청 | 이름으로 바꾼 요청 |
| --- | --- |
| "계산 중이면 기다려 달라는 게 나오면 좋겠어" | 추천 중에는 **스켈레톤 로딩**과 계산 중 안내를 보여주고, 분석이 끝나면 결과로 바꿔 줘 |
| "저장했다는 게 위에만 떠서 안 보여" | 저장 성공은 화면 하단 **토스트**로 3초, 실패는 버튼 아래에 남겨 줘 |
| "계산하러 가기 누르면 옆으로 넘어갔으면" | 첫 화면 **히어로 섹션**의 **CTA**를 누르면 계획 화면이 옆으로 밀려 들어오게 하고, 뒤로가기로 돌아오게 해 줘 |

## 6. AI와 일하면서 내가 정한 것

이번에는 Claude Code에게 기능 구현과 테스트, 배포 확인을 맡겼다. 결과를 직접 써 보고, 마음에 들지 않는 부분은 다시 요청했다. 내가 정한 기준은 이런 것들이다.

- 확인할 수 없는 정보는 화면에 지어내지 않는다. 별점이 없으면 숨기고, 식비는 가정값 대신 직접 입력한다.
- 화면을 부드럽게, 토스 앱처럼 깔끔하게. 기능은 '계획 만들기 · 내 계획 · 좌석 메모'처럼 메뉴를 하나씩 늘리는 방식으로 넣는다.
- 구단 마스코트 캐릭터는 저작권이 있어서 넣지 않았고, 구단 로고는 사용 허락을 받은 파일만 넣었다.

자동 테스트는 98개이고, 새 경기장 8곳에서 실제로 추천을 돌려 구간별 도보 시간과 도착 시각을 다시 계산해 맞는지 확인했다.
